# CLAUDE.md

Arcade-faithful port of Mr. Do! (Universal 1982) to the ColecoVision + Super Game Module.

## Priorities (in order)
1. The complete arcade game logic, behaving identically to the arcade.
2. Full speed (60 Hz).
3. Graphics. One-colour sprites and simplified art are acceptable when they buy 1 or 2.

## Sources of truth
- `~/work/do_disassemble/mrdo_main.bin`: the arcade main-CPU ROM. This is the reference for all logic.
- `~/work/do_disassemble/msx/mrdo_msx.asm`: MSX2 port with the arcade code translated. Use it for hook points, known pitfalls and bug fixes; its renderer (V9938 bitmap) does not apply here.
- `~/work/do_disassemble/tools/`: Python tools (arcade gfx decode, level composition, `mrdo_xlate.py` translator, CV maze/sprite asset experiments).
- `~/work/mrdoarcade` branch `feat/arcade-logic-sgm`: an earlier CV+SGM attempt. Its sound engine (`mrdo_snd.asm`) plays the arcade note streams on the SN76489 plus the SGM AY. It uses tniASM syntax and a trimmed 12-row maze; do not copy the trim.

## Decisions
- **Playfield:** all 13 arcade cell rows are kept (208px of play area against 192px of screen). An 8px-step vertical camera (offsets 0/8/16) follows Mr. Do. The logic and maze data stay byte-identical to the arcade; all screen fitting happens in the renderer. Never trim rows or patch coordinates in the logic.
- **HUD:** the playfield is 24 tiles wide (cols 0-23); score, lives and EXTRA go in the 64px panel (cols 24-31), see the HUD notes below.
- **Camera and Screen 2 thirds:** all three thirds share ONE pattern table ($0000) and ONE colour table ($2000) through the R4/R3 masks (R4=$00, R3=$9F), so a camera shift needs no tile moves and a tile set is 2 x 1792 bytes. Nothing may write per-third tile data.
- **Playfield tile codes:** per colourway set, 0-162 generated (max 160 used), 163-175 the dessert score bg tiles $15-$21 (attr 9, written at pickup by $30FD into the plate cells $1CF/$1EF), 163 the dessert score's "00", 164 its other half (loaded at pickup from build/tiles/score.bin, hud.asm score_load), 165-171 HUD glyphs, 172-175 the resting apple over dirt (apples.asm), 176-179 the current dessert's plate (loaded on demand from the set's 48 plate tiles, hud.asm plate_load), 180-255 and 165-171 the HUD glyphs (83: white and grey scores, 2ND, EXTRA states incl. green collected letters and both markers). hud_upload runs after the set upload, so the HUD's codes win. A playfield set's count byte is 180, so upload_set leaves the HUD codes alone.
- **HUD** (src/hud.asm, tools/gen_hud.py): the arcade's HUD strips (native columns 29-31 and 0-2) are mirrored into the panel, MSX2 layout, by (fg attr, fg tile) -> glyph; written to both name tables with spaced writes. Repainted after every playfield set upload and every full-redraw flip (bulk repaints only count cells). Screens clear the panel to code 0.
- **VRAM free for tables:** $0800-$13FF (IDC uses $0800+) and $2800-$37FF; $1400-$16FF is the second name table.
- **Two name tables** ($1800 and $1400, R2 flips): a full redraw (camera move, new tile set, queue overflow) is drawn into the hidden one, then cells queued up to that point (`flip_mark`) are drained into it too, then R2 flips. While the arcade bulk-repaints (queue overflowing, >= 16 writes per vblank) the redraw waits, so no half-painted picture is ever shown. A tile-set change uploads both tables in one NMI with the display blanked and the backdrop in the new set's main colour (~1 frame). The HUD panel (cols 24-31) must be written to BOTH name tables. During the dessert sequence ($E000 bit 3) the upload waits (up to 60 vblanks) until Mr. Do leaves the sprite queue, so its blank frame falls inside the arcade's own hidden stretch instead of blinking him.
- **Sprites:** one colour per sprite for now; upgrade (e.g. a two-colour Mr. Do) only once the game runs at full speed with the complete logic. All rotations and flips are pre-drawn in ROM (the TMS9918 cannot flip).
- **Design load:** 7 monsters + 3 chompers + Mr. Do + ball + 5 apples on screen at once.
- **4-per-line limit:** this is the TMS9918's own limit; the SGM does not change the video chip. Strategy:
  1. Take objects out of the sprite list where it's cheap: draw grid-aligned static objects (e.g. resting apples) as background tiles, using SGM RAM for the extra tile data.
     Done for apples (src/apples.asm): a resting apple ($5E, line 5, on the 8-px grid over 2x2 cells of undug dirt, fg $77) is left out of the sprite list and drawn with codes 172-175 (the apple sprite's pixels over the colourway's dirt, gen_tiles.py); apple_sync redraws the changed cells in the vblank the sprite list changes, so the handover to the wobbling/falling sprite shows no gap. List rows are kept + cam (camera-free). While a full redraw is pending, under way or waiting to be shown, apples stay sprites and apl_redraw4 queues its cells (drawn directly they went to the table on screen and missed the one being built: an apple stayed invisible after a camera move until touched); tools/sprite_check.sh also checks every tiled apple is on screen (longest gap 1 vblank). Cost: the sprite pass checks the code first (.nb) and calls apple_try only for $5E, which works from the raw entry (tx = 28 - Y/8, list row = 30 - X/8) before any position work; an apple tiled last pass at the same place and list index skips the 4-cell dirt check unless apple_at has drawn a tiled apple cell since (apl_inval). Uncached, the checks cost ~9k T a vblank (HEAVY bench 6656 vblanks vs 5266 without apple tiles); now 5250. Attract demo: 89% of apple-frames are tiles, crowded frames 3.5% -> 2.2%. The dessert score's digit halves moved to score.bin (loaded into code 164) to make room.
  2. Multiplex the rest (src/sprites.asm): count sprites per 8-line band; with no band at 5+, the SAT goes out in list order (no flicker at all). Otherwise: pinned sprites first (Mr. Do, codes $00-$26 via build/sprites/pin.bin), then sprites in uncrowded bands (never flicker), then the crowded ones rotated 3 places per frame in arcade order. The full row-cluster sort was tried and cost too much CPU; tools/flicker_sim.py shows crowded-rotate-3 matches it except the 5-in-a-row case.
  3. Draw one in four ball-code ($70) sprites: the ball's 20-fragment burst (and its re-form) was ~42k T-states per frame. Visual only; the logic is untouched.
  2b. Cost (chomper sessions, profiled 2026-09-28): a crowded screen re-sends the SAT every vblank even when the arcade lags; those vblanks now skip the list rebuild and reuse the last pass's split (sprites_prio classifies into unc_idx/crowd_idx once, spr_emit outputs). Pinned entries carry bit 6 in the list's colour byte (the TMS9918 ignores bits 4-6 there). The HUD's EXTRA marker is found by the sprite pass (hud_mk) instead of a queue scan per vblank. HEAVY bench 5250 -> 4182 vblanks. **After any change to src/sprites.asm or src/apples.asm run `tools/sprite_check.sh`** (every list build vs the on-screen count from arcade sprite RAM; must be 0 mismatches): twice a pass silently dropped sprites (a Z flag lost to `dec l`; carry left by `cp APPLE_CODE`) and the bench looked faster for it.
  4. SAT writes are spaced >= 30 T-states apart because the sprite pass can run past the end of vblank, where the TMS9918 drops faster writes.

## Arcade execution model (measured in MAME, 2026-09-27)
- Z80 4.1 MHz, 59.943 Hz: 68,398 cycles/frame. CV: 3.58 MHz, 59,659 T-states/frame.
- IM1; $0038 → IRQ handler $00B8. The main loop is only `jr $` at $00AC. All logic runs in the handler, which runs with interrupts off. The arcade IRQ is level-held, so an overrunning frame's IRQ fires as soon as `ei` runs.
- At handler exit, flags in $E001 either return ($0136) or discard the interrupted context and start the background pathfinder with interrupts on ($0138→$54EC maze search, $0141→$558E, $014D→$5647, which ends in a second idle loop at $0154). The pathfinder sets SP to $EB80/$EB76; the stack starts at $EB80.
- Map: $8000-$87FF bg video RAM, $8800-$8FFF fg video RAM, $9000-$90FF sprite RAM, $9800 flip, $9801/$9802 SN76489 x2, $9803 protection PAL, $A000-$A003 inputs/DIP switches, $E000-$EFFF work RAM, $F000/$F800 scroll.
- Gameplay handler cost: mean ~30.6k, p95 44.8k, max 73.2k cycles, so it fits the CV frame except about 0.1-0.4% of frames. The pathfinder takes about 56k cycles every ~30 frames and delivers results ~1 frame later than on the arcade.
- **Worst case** (level 5+, 8 monster slots, not 7; invincibility pokes in MAME): 8 monsters idle, median 63.7k / p95 70.3k; 8 monsters + 3 chompers, median 52.6k / max 79.7k; 6+ monsters + a falling apple, median 54.5k. Cost is about 6-7k cycles per monster. The unmodified logic cannot hold 60 Hz on the CV in heavy rounds (the budget is ~54k after VDP work). Hot routines must be hand-optimised, with the frame-by-frame RAM diff against MAME proving they behave identically.
- **Hotspots** (8 monsters idle, 66k/frame; profile in tools/profile): actor_update $3231 is 67% inclusive. Most of that is 12-slot object-table scans through IY, repeated for every monster: $1F78 apple_wobble 8.6k, $40AA monster-vs-objects 10.4k excl., $41EC/$48F2 chomper scans 5.5k/6.0k. Then the sound tick $5A90 (IX bit tests over 38 slots) 4.3k, and queue sprite $0297 + upload $026D 7.6k (replaced by our own sprite path). Target saving is about 12k per frame for the median and 16-17k for p95.
- **Speed patches** (tools/patch_arcade.py `speed_patches`, slow paths in src/opt.asm behind the jump table at OPT_BASE $BD00; `NOSPEED=1` builds without them for A/B): sound tick $5A90 fast idle scan, and no scan at all unless a request was posted since (snd_req at $59CB, ROM padding: set by hooks at the only request writers $02E6/$02F1 (game) and $5C66 (engine), kept set while a request stays pending); the handler's sprite RAM copy ($00C8) via opt_spr_copy, which sets `spr_new` so sprites_update skips vblanks with no new sprite data (an overrunning handler gets that time back). The video fill $046C/$046D (attr + tile $29 over a rectangle; the coin-up clear is ~1800 cells) goes to fill_046c: fills of 8x8+ cells inside video RAM store directly and set redraw_all (holding q_busy at $FF until the last row) instead of ~3600 hooked stores; post-coin logic stall 33 -> 10 frames. $7076 enters at $046D with its own A, so the jump sits at $046D.
- **Speed measurement:** `tools/bench.sh` replays a HEAVY lockstep recording (`HEAVY=1 make validate FRAMES=3000 SEED=3`: level 5, invincible via `jr nc`->`jr` at $32A6/$44B0/$4B94, alpha forced every 600 handlers) on the validation build: deterministic arcade handler times and the vblanks the replay takes. `tools/perf_sample.tcl` + `tools/perf_report.py` give a sampled exclusive profile. Baseline 6d8a0d2: 5067 vblanks, handler mean 47977 T.
- **Optimisation rule:** a rewritten routine must leave arcade work RAM ($6000-$6FFF mirror) byte-identical to MAME every frame. Speed-up side structures (e.g. an active-object list) live outside that mirror and are maintained at every write site.
- Sprite queue at $E311 (copied verbatim to $9000 by $026E): byte 0 code, 1 Y (drawn at 256-Y, 0 = unused), 2 colour (low nibble) + flip bits $10/$20, 3 X. Player-view row = constant arcade X. Apples are sprites (code $5E). Live sprites: normal play max 31 / p99 22; worst row normal play p99 5, max 9. 20 × code $70 fragments appear when the ball re-forms. Distinct (code, flip) per round can reach 187, so the SPT needs a per-frame cache (~17 new per frame at most), not a static set.
- **Pathfinder starvation guard** (`take_irq`, normal build only): when the handler overruns every frame (chomper session: 62-88k T with our NMI), each held vblank is taken at the handler's own exit, so the background pathfinder never runs an instruction and monsters/chompers never get a route (they sat in the nest). After 2 back-to-back held deliveries that would preempt real background work (a pathfinder `call`, or a `ret` into anything but the idle loops $00AC/$0154) the 3rd is skipped (`pf_drops` counts them); the background then runs until the next NMI. Ordinary play: 0 skips in 21 s; a forced chomper session: ~35 skips in its heaviest 4 s. The real fix is the hotspot work below.
- Port consequence: the CV vblank is an NMI (unmaskable). The NMI handler must copy the RAM buffers to VRAM first. It then runs the arcade handler only if that handler is not already running; if it is, it sets a pending flag, which the translated code services at its `ei` points (this imitates the level-held IRQ). The pathfinder's context discard and SP reset must be kept exactly.

## Target hardware
- ColecoVision + Super Game Module, on MegaCart cartridge boards. The user has an SGM and a flash cart for testing real-hardware builds; test on hardware as soon as the renderer exists (the VDP needs ~8µs between VRAM writes during active display). openMSX does drop writes that come too fast: unspaced writes "inside vblank" corrupted cutscene tiles whenever the NMI ran late, so keep every VRAM write spaced >= 29-30 T unless the display is blanked.
- The game must detect a missing SGM and show a "Super Game Module required" screen.

## How the arcade program runs (Phase 1)
- The arcade main ROM runs at its ORIGINAL addresses: `tools/patch_arcade.py` copies $0000-$5FFF into SGM RAM and rewrites only operands that point at moved things (work RAM $E000->$6000, video $8000->$7000, I/O and scroll -> RAM cells, sound data and scene code $6000-$7FFF -> MegaCart window bank 0). Instruction lengths and timing are unchanged. Every patch is listed in `build/arc_patches.txt`.
- The code map (`tools/codemap.py`) seeds from the Ghidra entries (`tools/data/ghidra_functions.txt`) plus jump-table targets and every instruction MAME executed (`tools/data/extra_entries.txt`). Code missing from the map is left unpatched. That caused a real bug (jump-table state handlers), so after any sweep, re-check that "executed but unmapped" is 0.
- Constants that only look like addresses (sprite code/colour pairs, positions, bit masks, negative offsets such as `$FFE0`) are listed in `KEEP_IMM` after review. Values of $F000 and up are never relocated unless they are exact scroll-register memory operands.
- Vblank: every arcade `ei` became `rst $08`. The NMI either enters the arcade handler directly (interrupts were on) or holds the vblank by rewriting $0008 to `jp take_irq`. Delivery mimics the Z80's one-instruction EI delay (`irq_after_ei` finishes the `ret` or `call` that follows the `ei`); the arcade's `ld sp,$EB76` resume path depends on the exact stack layout.
- **MegaCart hotspot:** reading $FFC0-$FFFF switches banks, so no switchable bank may keep data in its last 64 bytes. `tools/check_rom.py` enforces this on every build. The arcade image is stored 8KB per bank.
- Arcade writes into ROM addresses are ignored on the board but would corrupt our RAM copy of the code. The known one ($1761, write to $DC1A) is patched out.
- **ROM checksums:** the arcade sums $0485-$049E + $0547-$054E (must be $4F, $19FA) and $770B-$774C (must be $DF, $74BB). Our patches (PAL checks, video hooks) change those bytes, so `fix_checksums` sets each compare's operand to the patched sum (last step of patch_arcade). A failing first check stops the level counters $E09F/$E0A0 at round end.
- **Data records read by video routines** ($03D4/$0403/$0425 and scene pointer tables $73FC/$78C3) are relocated from recorded reads (tools/profile/sweep/rom_data_reads.json). The cutscenes were missing from that sweep: `tools/capture/scene_record.lua` with `DATAOUT=` (and `EXECOUT=` for the code map) records them; merge new scenes' reads into the json.

## Sound
- The arcade's own sound engine runs unchanged; src/sound.asm translates its chip writes: chip 1 ($9801) -> CV SN76489, chip 2 ($9802) -> SGM AY (tone periods x7/8 for the clocks; chip 2's noise shares AY channel C). Patches (normal build only): the `ld (bc),a` chip stores -> rst $10, `ld ($9801/2),a` at $5AE7/$5AEE -> snd_w1/snd_w2.
- The engine's per-channel output ($5C0F, normal build) goes through snd_chout: a tone channel is written only when its (iy+8)/(iy+9) or type class changed (records at $56F0-$56FE, the only free bytes left: DRV_RAM $59D0-$5A7F is full, and $59CB is snd_req); noise channels always (an SN noise-control write restarts the noise). The engine's per-tick silencing of idle channels ($5AE7/$5AEE -> snd_sil1/2) passes once per channel until it is written again. **After any sound change run `tools/sound_check.sh`** (every skipped write must be a true repeat: bad=0).
- The sound tick $5A90 runs from our NMI once per vblank (snd_sched -> snd_nmi_tick; the handler's `call $5A90` at $00D2 is NOPed), so music keeps tempo when the logic lags. It runs at the START of the NMI, before the drawing, and also in a nested NMI when our drawing overran a frame (snd_busy guards re-entry; the bank is saved and ARC_HI_BANK mapped): after the drawing, a tile-set upload + full redraw at round start / chomper start cost 2-3 ticks and a catch-up burst (audible hitch). Now exactly one tick per vblank there. Race-free: the game only posts requests with single stores ($02D9/$02EA), and every chip write is inside the tick. The validation build keeps the arcade's handler-driven tick.

## Lockstep validation
- `make validate FRAMES=n SEED=s` records n vblank handlers in MAME (`tools/diff/mame_record.lua`, scripted random play), replays the same inputs on `build/mrdo_validate.rom` in openMSX (`tools/diff/cv_replay.tcl`), and compares work RAM plus video RAM at the same sync point of every handler (`tools/diff/compare.py`). Relocated pointers held in RAM compare as equal.
- Validation mode runs the background pathfinder to completion with the vblank held off, identically in both emulators. Otherwise the result depends on CPU speed (the arcade's pathfinder progress per frame is a function of its 4 MHz Z80) and the RAM diverges for timing reasons alone.
- MAME inputs are injected by the read tap and latched at handler start.
- `SCEN=vg|w|dia|ext POKEH=h make validate ...` ends the round into that cutscene at handler h on both sides (same pokes at the same handler). All four scenes validate identical over 2200 handlers. MAME's own input system updates once per frame, which can land mid-handler.
- Non-gameplay screens (title, instruction) are captured from MAME with `tools/capture_screen.py NAME CAM REC:first-last --not REC:ranges` (`NOCOIN=1 NOSTART=1` recordings leave the attract sequence running) and listed in `SCREENS` in tools/gen_screens.py; the first signature match wins, so a screen whose signature also shows elsewhere (the title's logo) goes last.
- **Cutscenes with scrolling art** (src/scene.asm): the arcade scrolls the whole bg layer ($F800, along the player-view x axis) under the fixed fg text; the characters sit in a few band rows with no fg over them. Captured with `tools/capture/scene_record.lua` (per video frame + scroll log; SCEN=vg pokes a VERY GOOD round end) and `capture_screen.py NAME CAM scene:PREFIX:f0-f1 --band R0-R1 --not ...`. gen_screens pre-shifts every (left, right) bg pair to phases 0/2/4/6 in one bank per scene (hash by `pkey`). Runtime: per band row a 32-bit art mask + a VRAM cache (IDC, $0800) of the pair id per native row, invalidated by scene_mark on arcade writes and looked up lazily; a build gives each art cell the next slot of the off-screen slot bank (2 x 70 codes after the static set), then the next vblank flushes tiles (back to back inside vblank, spaced after) and names. 2-pixel steps; heavy builds (> 24 tiles) split the flush and build over more vblanks. VERY GOOD: 467 vblanks for the arcade's 421 handlers (finale ~94% speed).
- **Title / instruction logo** (src/logo.asm, gen_screens.py romhack_logo, capture_screen.py --logo 1-8:2-21): the romhack's Graphics I logo (8 x 20 tiles) replaces the arcade logo's cells (left out of the captures) at screen rows 1-8, columns 2-21; its 116 tiles sit at codes LOGO_BASE (108)-223 of those screens' sets; logo_cell answers for the region in both draw paths; logo_tick rewrites each tile's colour when the romhack's 12 colour-table frames change it (4 vblanks a frame, 0-5 then 6-11 looping).
- **Diamond scene clown** (src/logo.asm clown_*, gen_screens.py romhack_clown): the romhack's clown (7x10) and diamond (4x3, 3 frames, 8 vblanks each) over screen rows 4-16, columns 1-8 (the romhack layout 4 rows down, 1 right); its 75 tiles at codes CLOWN_BASE (149)-223 of the diamond set (cells seen only in that box dropped from diamond.txt); its 10 clown + 5 sparkle sprites replace the sprite pass on that screen (index byte 14 = 2); the arcade's credit token ($6D, from ARC_SPRITES) is added as SAT entry 0 so it draws over them and never loses a line to the 4-sprite limit.
- **Cherries** (tools/gen_tiles.py cherry_design): designed per level look (13 dirt pairs) instead of composing the arcade layers: tools/data/cherries.json (Cherry Lab saves, imported with tools/cherry_import.py) or the Cherry Lab's draft (the user's pick): per 8-pixel half-row the colour pair covering the most weight (cherry pixels 3x), other colours to the nearer of the two. (Tiled side by side, the red edge patches of neighbouring cherries meet in some levels; a black fill was tried and rejected.) The part-dug cherry tiles (a quarter's dig-morph outputs $94-$9B/$DC-$E3, cherry_dug) are built from the same design: pixels the arcade draws like the whole quarter keep the design, the bite takes the arcade colour, rows reduced again (bite weight 5). Cherry Lab: artifacts/19-cherry-lab, https://claude.ai/artifact/WiiYJN5jCUntQSFhNDJcW2 (db collection `cherries`, docs {pixels, pair}).
- **VERY GOOD characters** (src/vgland.asm, gen_images.py vgland -> bank 29 $E000): the band builds only the letter monster (vgl_filter drops native rows 7-22); the romhack's 14x5 Mr. Do/apple/dinosaur picture is patched into the band names at every build (vgl_patch) at column 5 - ceil(scroll/8), its 59 tiles in codes scn_base + 2*SCN_SLOTS (SCN_SLOTS = 50; the letter monster needs <= 20), 10 sprites moved with it (early clock at the left edge), legs every 8 vblanks. A row is only patched while the arcade still has character art in it. **Round-end icons**: the arcade queues one sprite per SCENE line for how the round ended ($2D creep, $6E cherries, $69 diamond, $51 letter monster); the sprite pass is off on this screen, so vgl_icons draws the romhack's 2x3 tile icon (PRINT_ICON; 22 tiles at vgl_base-22.., the top of the second slot bank) at that sprite's place in both name tables every vblank, plus its black overlay sprite (cherries, creep) in SAT entries 10-12 (vgland.bin +$800..$B1F; upload steps 4-5), 8 px right of the arcade's place. The lines are 16 px apart and the icons 24 px tall, so an icon's bottom row shares cells with the next one's top row; their pixels never share a line, so those cells get merged tiles (ORed patterns, per-line colour from the tile with pixels) in codes scn_base+44..49, re-uploaded when the pair changes.
- **Screen wipes go black** (opt.asm fill_fast -> blank_req -> render.asm go_black): a 32x24+ fill while a captured screen is up means the arcade is clearing it; the display goes black, mode none, until the next tile set is up (scr_hold keeps the old signature from matching for 16 vblanks). Before, the NMI kept rendering the dying screen and the band kept tracking it: VERY GOOD -> level took ~3.5 s instead of ~0.5 s.
- **Nested NMI ack:** reading the VDP status resets its address latch, so an NMI that arrives while our NMI work is still running must not ack (a write between the two address bytes lands elsewhere: a stray HUD glyph in the playfield). It sets nmi_late; late_ack pays it at safe points (render phases, per redraw row, per drained cell, per HUD cell, NMI end); without the drain one the boot test counts 210 vblanks instead of 228.
- **EXTRA pan** (image.asm extra_check / img_pan): the arcade opens EXTRA by setting its bg scroll to 224 (why $E0C7 = 4) and scrolls 64 px to 32 at 0.5 px a frame. The romhack picture goes up at that first frame (during the arcade's own blank screen) with rows 6-23 shifted right by img_d tiles (8 -> 0, filler = each row's column 5), each step pre-written into the hidden name table and flipped when the scroll reaches it; sprites move with it; the flag waves after. check_screens ignores the captured congrats/extra screens while it is up (they still match for a few frames while the arcade clears them at the end). Leaving it keeps the display blanked and black until the next tile set is up, and a playfield that follows a screen or image uploads with a black backdrop (up_black; between two playfields the backdrop stays the new dirt colour). Variables after SCN_LIST (img_d/img_bd/img_brow).
- **EXTRA scene: the romhack's picture** (tools/gen_images.py -> bank 29, src/image.asm): a screen whose index entry has an image bank (byte 13, gen_screens IMAGES) switches to MODE_IMAGE: picture, both name tables, the romhack's 22 sprites, its flag animation; sprite pass and drawing pause; leaving clears both name tables and the sprite cache.
- The diamond (CONGRATULATIONS / SPECIAL) scene is a plain captured screen (no motion: the bg is drawn unscrolled, characters at their resting places); `congrats` covers the CONGRATULATIONS opening both share and is listed after them. A hash miss falls back to the cell's bg alone, then its fg alone, then black.
- RAM validation cannot see rendering bugs. `tools/diff/compare_frames.sh SEED CAM H1 H2 ...` captures MAME and the normal build at the same handlers and writes a side-by-side sheet (build/frames.png) with a per-frame pixel agreement (baseline ~81% with correct sprites; a sprite placement bug shows up at a glance).
- Debug aids (env vars): `WATCH=addr` (MAME: arcade address; openMSX: CV address) logs writes with PC and handler; `RTRACE`, `ITRACE`, `HTRACE` trace fg-tile reads, input reads and handler entries.

## Build and test
- **Always run MAME with `SDL_VIDEODRIVER=dummy SDL_AUDIODRIVER=dummy`** (plus `-video none -sound none`). Without it MAME activates as a macOS GUI app and pulls the user's screen to another Space. Recordings and `-snapshot_directory` screenshots work the same. openMSX is fine as is.
- `make`: SjASMPlus builds `build/mrdo.rom` (256KB MegaCart image). `make run` starts openMSX. `make test` boots headless-ish for 4 emulated seconds, prints the self-test verdicts and saves `build/boot.png`.
- openMSX machine `ColecoVision_SGM`, romtype `ColecoMegaCart`. openMSX Tcl scripts read symbols from `build/mrdo.sym`. Set `throttle on` for a few frames before `screenshot`, otherwise the capture is black.
- Generated data goes to `build/` (created by `tools/*.py`, which import the do_disassemble tools via `$DO_DISASM`, default `~/work/do_disassemble`).

## Hardware layout (see `src/hw.inc`)
- MegaCart: the last 16KB bank is fixed at $8000-$BFFF; reading $FFC0+n maps bank n at $C000-$FFFF. Bank-switching code runs from the fixed bank or RAM.
- SGM: `out ($53),1` gives 24KB RAM at $2000-$7FFF; `out ($7F),$0D` swaps the BIOS out for 8KB RAM at $0000-$1FFF. After boot the BIOS is gone; our vectors live at $0000/$0038/$0066.
- VRAM: PT $0000, PNT $1800, SAT $1B00, CT $2000 (full 6KB), SPT $3800.
- Once the display is on, only the NMI (vblank) handler touches the VDP. The main loop works in RAM buffers.
- Arcade work RAM $E000-$EFFF is rebased to $6000-$6FFF (same low 12 bits) so emulator RAM dumps can be diffed against MAME directly.
